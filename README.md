> **v2 (2026 rebuild).** The original prototype's code was not preserved; this is a clean re-implementation of the same design. Numbers in this README come from this codebase.

## The thirty-second version

A lecture or meeting recording goes in; clean, structured notes come out. The transcription itself
runs **entirely on your machine** through [Vosk](https://alphacephei.com/vosk/) — no account, no key,
no upload, no per-minute cost. If you *do* set a Gemini key, the raw transcript gets formatted into
headings, bullets, key terms and action items, and a screenshot button can grab the slide in front of
you and answer a typed question about it. Without a key, a rule-based formatter still produces usable
notes and the screenshot question is stored unanswered rather than silently dropped.

The split matters, so it is stated plainly wherever this project is described: **transcription is
always offline; formatting and screenshot Q&A use Gemini only when you enable them.**

What actually shipped:

```
AudioSource (File | Mic, pausable, bounded) → Vosk wrapper → TranscriptStore (partial + final)
          ↓                                                        ↓
   CLI (--file/--mic)                                     Formatter (RuleBased | Gemini)
          ↓                                                        ↓
   JavaFX UI (Record/Pause/Stop/Screenshot, transcript + notes panes) → NotesDocument
          ↓                                                        ↓
   ScreenCapture (java.awt.Robot) → QAService (Gemini) → NotesDocument.withAttachments
          ↓
   Exporter (Markdown | PDF) → notes.md, notes.pdf, transcript.txt
          ↓
   eval/ (WER, real-time factor, keyword recall) → results.md, generated by scripts/run_eval.sh
```

**The large model was not worth it here.** It is 45× the download (1.8 GB zipped vs 40 MB), twice the
processing time (39.3 s against 19.7 s for the same audio), and gained 0.1 percentage points of mean
WER — inside the noise of 25 word errors. The small model stays the default; the large one is
documented for anyone who wants to try it and generate their own numbers rather than trust these.
Both runs are committed in full: [`eval/results.md`](eval/results.md) (small) and
[`eval/results-large.md`](eval/results-large.md).

**The offline formatter's key terms are weak, and now there is a number for it: 12.9%.** Of the 31
rubric phrases the recogniser heard across the five fixtures, 4 were surfaced as key terms — `hit
rate` and `query plan` among them. Read that number with two things in mind, both stated in the
report itself: every fixture is about forty seconds long and most of the rubric's phrases are used
**exactly once** in that time, and a repetition-based extractor cannot surface a phrase that never
repeats; a twenty-minute lecture is the case the extractor is built for, and these clips are its
floor case. The rubric is also 39 phrases written for *recognition*, so statistics like "eighty four
percent" count against the formatter even though a key-term list arguably should not contain them.

What did change, on the same fixture, is visible rather than statistical. Before, the extractor could
only ever emit single words and produced `expiry, minute, percent, reached, cash, data, hit, rate`;
now it emits repeated phrases with a cohesion and topic-position score:
`minute expiry, hit rate, percent, cash, data, week` — one term where `hit` and `rate` used to be two,
bolded as one run. The junk that the first attempt at this produced (`expiry reached`, `minute expiry
reached`, from a template sentence that repeats) is why a term may no longer end in `-ed`; that rule is
a heuristic, not grammar, and it keeps `fixed`-style modifiers (`fixed cost` would otherwise be
lost) while dropping past-tense tails.

**What the recogniser hears is imperfect, and the misses are listed rather than hidden.** From
[`eval/results.md`](eval/results.md): `caching` → *cashing*, `a bet` → *a bed*, `two weak caches` →
*to we caches*, `still weak` → *still week*, and the rubric phrases *cache*, *payday*, *coverage
badge*, *practise three problems*, *table scan*, *writes slower* were missed outright. The full
verbatim transcript of one fixture is quoted there, not just the score.

**The rule-based notes are plainly rougher than the transcript**, and this is the honest example.
Real output from `--file eval/audio/lecture-01-caching.wav`, notes pane and all:

```markdown
## Notes

This lecture is about cashing in web systems

In our experiment a one **minute expiry** reached eighty four **percent** …

## Key terms

minute expiry, hit rate, percent, cash, data, week
```

Four things a reader would notice, all of them limitations rather than bugs to hide. The topic word
reaches the notes as *cashing* and *cash*, because that is what the recogniser heard. The key terms
include *percent* and *week*, which are not ideas. The paragraph splitter follows pauses, and the pause
between "ninety one percent" and "action instrument the hit rate" is shorter than the one-second
threshold, so the experiment and the instruction arrive as one 31-word paragraph — and the instruction
then appears again in **Action items**, which is the extractor doing what it says: a paragraph is where
the speaker breathed, an action item is what the cue word marked. And the term `minute expiry` starts
one word late ("a one minute expiry"); phrases are built from content words, so `one` is dropped. Each
of those is listed below.

## Architecture

```
src/main/java/io/github/mit37/speechnotes/
  audio/       AudioSource, FileAudioSource, MicAudioSource, PausableAudioSource,
               LimitedAudioSource, AudioSourceFactory  (16 kHz mono PCM16 everywhere)
  transcribe/  Transcriber interface, VoskTranscriber, TranscriptListener
  pipeline/    TranscriptStore (events), TranscriptionPipeline (source → text → notes)
  notes/       Transcript, NotesDocument, NoteSection, ActionItem, NoteAttachment
  format/      Formatter, RuleBasedFormatter, GeminiFormatter, GeminiPrompts, MarkdownNotesParser
  gemini/      GeminiConfig (env + caps), GeminiBudget, GeminiClient, HttpGeminiClient
  qa/          QAService, GeminiQaService
  capture/     ScreenCapture, RobotScreenCapture
  export/      NoteFormatting, MarkdownExporter, PdfExporter
  ui/          SpeechNotesApp, MainView, RecordViewModel, LiveSessionService, SessionService
  cli/         CliArgs, Command, Options, ExportFormat, FormatterChoice, UsageException
  eval/        WordErrorRate, EvalFixture(s), EvalRunner, EvalMain
  CliMain.java exit codes: 0 done · 1 failed (missing model, unreadable audio, no device, a
               refused Gemini request, a write error) · 64 wrong command line (BSD sysexits)
```

Ground rule the whole thing is built on: nothing in `audio/`, `transcribe/` or `format/RuleBasedFormatter`
can reach the network, and `gemini/` is the only package that opens a socket — behind a key check, a
per-run request cap and a per-run character cap.

## Running it

Five commands, no key anywhere, and they work on a clean clone after one model download:

```bash
git clone https://github.com/mit37/speech-notes-java && cd speech-notes-java
./gradlew build                                  # compiles, tests, Spotless, Checkstyle
scripts/download_model.sh                        # 40 MB Vosk model, checksum-verified, Apache 2.0
./gradlew run --args="--file eval/audio/lecture-01-caching.wav"   # notes to stdout, offline
./gradlew run --args="--ui"                      # the desktop UI, record button and all
scripts/run_eval.sh                              # regenerates every number in Results
```

`./gradlew run` reports the app's non-zero exit codes as a failed build, so when the exit code itself
is what you care about use a plain launcher — `./gradlew installDist` writes one to
`build/install/speech-notes-java/bin/`, and `scripts/package_app.sh` produces a double-clickable app
image carrying its own runtime (installers need the platform's tooling: WiX for `msi`, `fakeroot` for
`deb`).

The CLI surface, verbatim from `--help`:

```
Commands
  --file <audio>     transcribe an audio file (WAV or MP3), offline
  --mic              transcribe the microphone, offline
  --ui               open the desktop UI
  -V, --version      print the version and exit
  -h, --help         print this help and exit

Options
  --out <dir>        write the notes and transcript.txt there instead of printing notes
  --export <how>     md (default), pdf, or both — needs --out
  --model <dir>      Vosk model directory (default: models/vosk-model-small-en-us-0.15)
  --seconds <n>      stop microphone recording after n seconds
  --format <how>     rule (default, offline) or gemini (needs GEMINI_API_KEY)
  --dry-run          show the Gemini request without sending it, and stay offline
  --no-actions       leave out the action-item section
  --title <text>     notes title (default: derived from the file name)
```

Asking for `--format gemini` with no key exits 1 and says how to fix it (`set GEMINI_API_KEY`, or add
`--dry-run` to see the request without sending it) — it does not quietly fall back to the offline
formatter and pretend. The UI is the opposite on purpose: with no key it formats with the rule-based
formatter and says so in the status line.

That block is the script's output verbatim, so refreshing it after a change is a copy-paste. What the
suite covers, by area: CLI grammar and exit codes (including end-to-end file runs against the real
model), the PCM16 conversion and file/mic sources, the Vosk wrapper against the committed fixture, the

The **two skips are deliberate, not broken tests**:

- *MP3 decode* — the decoder is bundled and verified to register itself, but no MP3 can be produced
  here (no `ffmpeg`/`lame` on this machine) and no binary fixture is committed for one, so the
  end-to-end MP3 path is asserted only when a fixture is present.
- *Real screen capture* — `RobotScreenCapture` is exercised for its no-display error path; the
  display-present path needs a display.

Golden files are checked in under `src/test/resources/golden/` and regenerated by
`scripts/regen_golden.sh`; both the Markdown and the PDF-text goldens are line-ending-normalised so
they hold on any platform.

Fixtures: `eval/audio/*.wav` are five 16 kHz mono WAV files generated on this machine from the
scripts in `eval/fixtures/` using Windows SAPI voices (`scripts/make_fixtures.ps1`) — synthetic speech
rather than a recorded lecture, so that the eval is reproducible and committable. What that does and
does not measure is stated at the bottom of [`eval/results.md`](eval/results.md).

## What this does not do

- **No speaker diarization.** Nobody is labelled; the transcript is one stream of text.
- **No cloud sync, no mobile, English only.** The model path is configurable, so another Vosk model
  can be dropped in, but no second language ships in v2.
- **Gemini is never used for transcription.** Only formatting and screenshot Q&A, only when a key is
  set, and always behind hard per-run caps (20 requests, 120 000 characters, 60 s timeout by
  default). `--dry-run` prints the request and sends nothing.
- **The offline formatter does not summarise, and its key-term recall is 12.9%.** It splits
  paragraphs, finds enumerations, pulls key terms and extracts action items — nothing more. Two
  measured weaknesses: key terms are drawn from what repeats (the Results section shows a real
  example, and the fixture-length caveat that comes with the number), and paragraphs follow pauses,
  so a speaker who never pauses gets one long paragraph up to the word cap. Key-term ranking also
  uses a documented heuristic: a term may not end in `-ed`, because a repeated template sentence was
  producing "expiry reached" as a term.
- **Gemini output quality is not measured.** CI runs with no key and a fake HTTP server; every claim
  about online formatting is a claim about wiring, caps and error handling, not about note quality.
- **Mic capture and real screen capture need hardware.** They are built behind interfaces and tested
  with fakes; the live behaviour is what [`docs/DEMO.md`](docs/DEMO.md) exists to record. Both are
  listed under "Cloud-instance constraints" in [`docs/PLAN.md`](docs/PLAN.md).
- **The screenshot hotkey is window-scoped, not a system-wide hook.** Ctrl/Cmd+Shift+S is a JavaFX
  accelerator: the window has to have focus, and what lands in the PNG is whatever is on screen at
  that instant. A global hotkey would mean a native library (JNI), which the PRD's stack does not
  include — so the hotkey is bound and tested, and the capture still means "bring the window forward
  first". The headless test asserts the binding, because Monocle does not route OS key events to
  accelerators.
- **The eval measures recognition, not note-taking.** WER, real-time factor and keyword recall say
  what the recogniser heard. Nobody has yet scored whether the notes are *useful*; that needs humans
  reading them, and five synthetic fixtures are not enough for it.
- **One machine's numbers.** Every timing here comes from the CPU that ran the scripts. Nothing is
  claimed about any other hardware.
- **The release is not tagged.** The code is pushed and CI is green, but there is no `v2.0.0`
  release yet, so the Release badge shows no version and the packaged app image is not attached to
  anything.

## Design decisions

- **Vosk small English model by default, large model optional and documented.** Chosen because it runs
  on a laptop CPU with no network and no GPU, ships under Apache 2.0, and is ~40 MB. Measured
  trade-off: the large model bought 0.1 pp of WER for 2.3× the time, so the default stays small and
  the large run is kept in the repo as evidence rather than as an upgrade path.
- **`Formatter` is an interface with an offline default.** The demo, the tests and CI must run with no
  key and no spend, so `RuleBasedFormatter` is the default and `GeminiFormatter` opts in. Trade-off:
  rule-based notes are honest but crude, and the CLI says so loudly instead of degrading silently.
- **CLI-first entry point, UI behind `--ui`.** The Definition of Done is a `--file` command that has to
  work headlessly, so the JavaFX window is a mode rather than the only way in. Trade-off: two entry
  paths to keep wired to the same pipeline, and one of them (the UI) cannot be fully tested without a
  display.
- **Model weights are downloaded, never committed, with a pinned SHA-256.** Keeps the repo small,
  keeps third-party weights out of git, and makes a corrupted or substituted download fail loudly.
  Trade-off: a fresh clone needs one ~40 MB fetch, or `SPEECH_NOTES_MODEL_ZIP` for an air-gapped copy.
- **Golden files instead of assertion-by-vibe for exports.** `MarkdownGoldenTest` and
  `PdfExporterTest` compare a fixed document against committed goldens, and the PDF is read back
  through PDFBox. Trade-off: a real formatting change requires regenerating both, which
  `scripts/regen_golden.sh` does.
- **Every number in this README comes from a script that anyone can rerun.** `scripts/test_count.sh`
  counts the JUnit XML, `scripts/run_eval.sh` writes `eval/results.md` from the committed fixtures.
  Trade-off: the README's Results section is a transcript of this machine's output, so it goes stale
  when the code changes — which is why CI prints the test count on every run.
